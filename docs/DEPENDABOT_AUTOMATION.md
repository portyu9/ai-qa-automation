# Dependabot automation authority

Dependency automation is deliberately narrower than ordinary CI success. The default-branch `dependency-governance` workflow is the only autonomous Dependabot merge authority.

## Green-path merge

Direct autonomous Dependabot merge is limited to GitHub Actions updates generated by the canonical Dependabot identity whose reviewed update metadata is one of the configured semver patch/minor/major version or security-update classes. Even then, only non-control-plane workflow action-pin replacements are admissible. Governance requires all of the following before merge:

- the pull request still targets the current `main` commit and is definitively mergeable;
- the head is repository-owned and the PR/commit identities match Dependabot's canonical numeric identity and email;
- the single Dependabot commit has GitHub's verified signature, canonical `web-flow` committer metadata, and the Dependabot sign-off/update metadata;
- every changed file is an existing workflow file and every changed patch line is a one-for-one immutable action SHA replacement for the same action identity with a strictly increasing annotated version and a changed immutable SHA; `manualReviewPaths` still marks control-plane surfaces, but this reviewed lane deliberately allows that narrow action-pin-only exception and rejects every other semantic change;
- `Required PR Gate` and `CodeQL` are green on the exact current head;
- no manual-review blocker label or protected control-plane path is present;
- after exact Trusted PR Gate revalidation, the write-capable controller publishes or reuses a durable exact-head `APPROVE` review from canonical `github-actions[bot]`, with the review body bound to the PR, base/head, prospective merge, trusted run, and trusted status id, then re-reads that review before mutation;
- the prospective merge ref still has the exact current base/head parents.

Python dependency PRs are **not merged directly**. `pipMode=promotion` treats their signed Dependabot intent as input to deterministic lock recompilation, then creates an exact synchronized promotion subject under `automation/dependency-promotion-...` using the independently configured non-certifying promotion-author App. Creation first pins an exact temporary `automation/dependency-promotion-base-...` ref to current reviewed `main`, opens the generated PR against that non-main base, re-proves App/head/base/control identity, retargets it to `main`, and removes the temporary ref. CI and CodeQL intentionally do not subscribe to the resulting `pull_request: edited` retarget; after exact controller-side retarget validation, the **same accepted-main governance run** publishes one neutral qualification wake bound to that run id/attempt, and only the successful completion of that exact run may wake Trusted PR Auto. The temporary base and neutral check are therefore liveness plumbing, never validation or merge authority. Any ambiguous or interrupted transition is retained or rolled back only under exact-ref ownership checks, and the existing staged-promotion reconciler resumes a proven interrupted subject. Pre-migration GitHub-Actions-authored promotion subjects are cleanup-only and are regenerated under the App. Dependabot native rebasing remains preferred; when a stale Python source PR's dependency-authority bytes are provably identical between its base and live `main`, the promotion compiler may safely use live `main` without rewriting the Dependabot branch, while overlapping authority drift remains blocked.

Repository merge policy requires exact dedicated-App `Trusted PR Gate` evidence before governed dependency mutation; live ruleset enforcement is externally administered and must be observed separately. Dependency governance never publishes that terminal authority itself. Direct Dependabot Actions merges require exact App-owned evidence from genuine Trusted PR Auto validation. A successful live-refetched CI run from the exact Dependabot identity may wake that validation only after its head resolves to one live same-repository `dependabot-actions` PR; the CI result is not merge authority, and the serialized five-minute schedule remains an independent liveness fallback. Generated dependency promotions may converge through either that schedule or the reviewed dependency-governance qualification `workflow_run`: governance first publishes one neutral exact-run qualification wake, Trusted PR Auto re-proves the promotion lineage and full validation graph, and its dedicated App publishes the exact-subject status. That App status is terminal evidence, not a GitHub `status`-event merge wake. Post-certification dependency convergence uses either the five-minute accepted-main reconciler or `dependency-trusted-merge.yml`, which is woken only by a completed successful Trusted PR Auto `workflow_run` from exact current accepted `main`. Its first job is physically read-only (`actions`, `contents`, `pull-requests`, and `statuses` read): it re-fetches the exact trusted run and repository identities, rebinds current `main`, scans only bounded live dependency candidates, and accepts at most one promotion or Dependabot Actions subject whose exact App-owned gate evidence points back to that same validating run. Only the closed lane and positive PR number cross the job boundary through inherited runner file descriptor 3; the resolver has no Environment, secret, or mutation authority and emits no subject data to stdout. A separate write-capable job validates that lane/PR pair and invokes the existing exact-target merger, which independently re-fetches the subject and re-proves actor/provenance policy, current base, prospective merge parents/tree, exact workflow identity/event/attempt, and dedicated App status immediately before SHA-guarded mutation. Missing, stale, malformed, or ambiguous evidence remains a no-op or hard failure.

After any governed dependency merge, the independent merger re-reads the actual merge commit and requires exact ordered base/head parents, a merge tree matching the validated dependency head, and the merge SHA as current `main`. `dependency-trusted-merge.yml` then runs the reviewed reusable full CI and CodeQL workflows **inside the same trusted merge workflow run**, bound to that newly observed accepted-main SHA. Its terminal `Dependency Post-Merge Required Gate` can publish the exact-run `Dependency Post-Merge Gate` check only after those two validation jobs succeed and it independently re-proves the live merge and control revision. A successful merge API response, no-op controller, or skipped job cannot substitute for that evidence.

The accepted-main `dependency-governance` fallback first performs the same read-only post-merge check. If validation is missing for an exact current dependency merge, governance invokes the reviewed reusable CI and CodeQL on the live subject in **its own run**, with a separate required gate, and does not admit further mutation until both succeed. All other main-mutating controllers use `dependency_recovery.py --check-post-merge` as a read-only barrier before mutation or credential minting, retaining fail-closed behavior for missing, pending, failed, ambiguous, stale, or replayed evidence. This isolates successive main writes from unvalidated dependency merges without depending on another downstream `workflow_run` delivery.

`post-merge-ci.yml` is a separate, secret-free accepted-main liveness/validation bridge listening only to its reviewed upstream `workflow_run` events. It **does not** accept `repository_dispatch` or `workflow_dispatch`, select untrusted subjects, merge PRs, publish `Trusted PR Gate`, or manufacture post-merge evidence. Its trusted-main binder independently verifies the exact native upstream workflow/run/attempt/merge commit and admits reusable CI and CodeQL only for a proven accepted-main advance. GitHub's nested `workflow_run` depth limitation is not a substitute for same-run validation: the protected-maintenance merger also invokes reusable CI and CodeQL before claiming its own terminal post-merge success. Only the isolated reusable CodeQL job receives `security-events: write`. The authenticated App gate and exact-head base/merge controls remain mandatory before any merge.

## Red-path recovery

Recovery has no merge or status authority. It may request at most one rerun (`maxRunAttempts == 2`) and only when all of these conditions are true:

- the PR first passes the same Dependabot identity, provenance, current-base, control-plane, and semantic-diff checks used by governance;
- the failed run is the reviewed CI workflow for the exact PR head;
- exactly one non-aggregate leaf job failed;
- exactly one step in that job failed and the step is in the code-owned infrastructure/upload allowlist;
- a timestamp-bounded slice of that failed step's logs contains an approved transient network/service signature;
- no deterministic dependency, policy, authentication/authorization, rate-limit, disk, or permission blocker appears in that same log slice.

Tests, deterministic evaluations, supply-chain assertions, security scans, browser assertions, CodeQL, and aggregate gates are never recovery targets. A second failed attempt stays red for manual investigation.

## Code scanning

`codeql.yml` runs Python CodeQL with `security-extended` queries on pull requests, `main`, a weekly schedule, and manual dispatch. External-fork pull requests do not receive write-capable code-scanning execution.

The read-only dependency post-merge barrier **first** checks for the independently re-fetched, canonical `Dependency Post-Merge Gate` success evidence emitted by the exact first-attempt trusted merge workflow after full same-run CI and CodeQL. A complete, correctly bound terminal proof does not require enumerating historical no-op bridge wakes; this prevents long-lived `main` revisions from becoming inoperable after hundreds of unrelated workflow completions. When no valid successful terminal proof exists, the barrier discovers historical workflow evidence through the specific, immutable `Post-Merge CI` workflow ID with an exact `head_sha` filter, not the repository-wide workflow-run collection. This prevents the unrelated security, Dependabot, and trusted-gate wake traffic on a long-lived `main` SHA from exhausting a bounded query before the relevant bridge runs are even considered. The finite pagination budget still fails closed on a genuinely saturated post-merge workflow; every candidate is subsequently fetched again and checked for exact event, repository, branch, identity, gate, and revision provenance. A successful no-op or skipped bridge remains non-authoritative.
