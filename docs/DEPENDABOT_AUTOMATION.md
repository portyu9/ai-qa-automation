# Dependabot automation authority

Dependency automation is deliberately narrower than ordinary CI success. The default-branch `dependency-governance` workflow is the only autonomous Dependabot merge authority.

## Green-path merge

Direct autonomous Dependabot merge is limited to GitHub Actions updates generated by the canonical Dependabot identity whose reviewed update metadata is one of the configured semver patch/minor/major version or security-update classes. Even then, only non-control-plane workflow action-pin replacements are admissible. Governance requires all of the following before merge:

- the pull request still targets the current `main` commit and is definitively mergeable;
- the head is repository-owned and the PR/commit identities match Dependabot's canonical numeric identity and email;
- the single Dependabot commit has GitHub's verified signature, canonical `web-flow` committer metadata, and the Dependabot sign-off/update metadata;
- every changed file is an existing workflow file and every changed patch line is a one-for-one immutable action SHA replacement for the same action identity with a strictly increasing annotated version and a changed immutable SHA; `manualReviewPaths` still marks control-plane surfaces, but this reviewed lane deliberately allows that narrow action-pin-only exception and rejects every other semantic change;
- `Required PR Gate` and `CodeQL` are green on the exact current head;
- no manual-review blocker label or protected control-plane path is present;
- the prospective merge ref still has the exact current base/head parents.

Python dependency PRs are **not merged directly**. `pipMode=promotion` treats their signed Dependabot intent as input to deterministic lock recompilation, then creates an exact synchronized promotion subject under `automation/dependency-promotion-...` using the independently configured non-certifying promotion-author App. Pre-migration GitHub-Actions-authored promotion subjects are cleanup-only and are regenerated under that App. Dependabot native rebasing remains preferred; when a stale Python source PR's dependency-authority bytes are provably identical between its base and live `main`, the promotion compiler may safely use live `main` without rewriting the Dependabot branch, while overlapping authority drift remains blocked.

Because `main` requires the dedicated `Trusted PR Gate`, dependency governance never publishes that terminal authority itself. Direct Dependabot Actions merges require exact App-owned evidence from genuine Trusted PR Auto validation. A successful live-refetched CI run from the exact Dependabot identity may wake that validation only after its head resolves to one live same-repository `dependabot-actions` PR; the CI result is not merge authority, and the serialized five-minute schedule remains an independent liveness fallback. Generated dependency promotions may converge through either that schedule or the reviewed dependency-governance qualification `workflow_run`: governance first publishes one neutral exact-run qualification wake, Trusted PR Auto re-proves the promotion lineage and full validation graph, and its dedicated App publishes the exact-subject status. That App status is terminal evidence, not a GitHub `status`-event merge wake. Post-certification dependency convergence uses either the five-minute accepted-main reconciler or `dependency-trusted-merge.yml`, which is woken only by a completed successful Trusted PR Auto `workflow_run` from exact current accepted `main`. Its first job is physically read-only (`actions`, `contents`, `pull-requests`, and `statuses` read): it re-fetches the exact trusted run and repository identities, rebinds current `main`, scans only bounded live dependency candidates, and accepts at most one promotion or Dependabot Actions subject whose exact App-owned gate evidence points back to that same validating run. Only the closed lane and positive PR number cross the job boundary through inherited runner file descriptor 3; the resolver has no Environment, secret, or mutation authority and emits no subject data to stdout. A separate write-capable job validates that lane/PR pair and invokes the existing exact-target merger, which independently re-fetches the subject and re-proves actor/provenance policy, current base, prospective merge parents/tree, exact workflow identity/event/attempt, and dedicated App status immediately before SHA-guarded mutation. Missing, stale, malformed, or ambiguous evidence remains a no-op or hard failure.

After any governed dependency merge, the controller re-reads the actual merge commit and requires exact ordered base/head parents, a merge tree identical to the validated dependency head, and the merge SHA as current `main`. It records that canonical accepted-main post-merge validation is pending rather than dispatching CI from the mutation job. Because repository `GITHUB_TOKEN` merges can suppress recursive workflow triggers, the separate accepted-main `post-merge-ci.yml` bridge is woken by successful `dependency-governance` or `Dependency Trusted Merge — ƳƤ AI QA Automation Framework` completion. The bridge proceeds only when the controller actually advanced `main`, then rebinds the exact controller run, live `main`, canonical governed merge identity and parents, and invokes the reviewed reusable CI and CodeQL workflows through `workflow_call`; unrelated, stale, no-merge, or multiply advanced subjects cannot be certified as the governed merge. The bridge has no merge, status, check, App-token, secret, or deployment authority, and only its CodeQL call receives isolated `security-events: write`. For Python promotions, `merged=true` records the controller's exact merge proof; post-merge CI/CodeQL remains separate revision-bound evidence and is never synthesized by the controller.

## Red-path recovery

Recovery has no merge or status authority. It may request at most one rerun (`maxRunAttempts == 2`) and only when all of these conditions are true:

- the PR first passes the same Dependabot identity, provenance, current-base, control-plane, and semantic-diff checks used by governance;
- the failed run is the reviewed CI workflow for the exact PR head;
- exactly one non-aggregate leaf job failed;
- exactly one step in that job failed and the step is in the code-owned infrastructure/upload allowlist;
- a timestamp-bounded slice of that failed step's logs contains an approved transient network/service signature;
- no deterministic dependency, policy, authentication/authorization, rate-limit, disk, or permission blocker appears in that same log slice.

Tests, deterministic evaluations, supply-chain assertions, security scans, browser assertions, CodeQL, and aggregate gates are never recovery targets. A second failed attempt stays red for manual investigation.

## Code scanning

`codeql.yml` runs Python CodeQL with `security-extended` queries on pull requests, `main`, a weekly schedule, and manual dispatch. External-fork pull requests do not receive write-capable code-scanning execution.
