# Dependabot automation authority

Dependency automation is deliberately narrower than ordinary CI success. Autonomous authority is split between default-branch `dependency-governance` for canonical Dependabot GitHub Actions updates and default-branch `dependency-promotion-author` for deterministic Python dependency promotions. Neither workflow may publish `Trusted PR Gate`.

## Green-path merge

Autonomous merge is limited to GitHub Actions patch/minor updates generated by the canonical Dependabot identity. Governance requires all of the following before merge:

- the pull request still targets the current `main` commit and is definitively mergeable;
- the head is repository-owned and the PR/commit identities match Dependabot's canonical numeric identity and email;
- the single Dependabot commit has GitHub's verified signature, canonical `web-flow` committer metadata, and the Dependabot sign-off/update metadata;
- every changed file is a non-control-plane workflow file and every changed patch line is a one-for-one immutable action SHA replacement for the same action and same major version;
- `Required PR Gate` and `CodeQL` are green on the exact current head;
- no manual-review blocker label or protected control-plane path is present;
- the prospective merge ref still has the exact current base/head parents.

Eligible Python dependency updates use a promotion path rather than mutating the Dependabot branch. The controller validates the exact signed Dependabot `pyproject.toml` intent, generates the reviewed wheel-only lock set plus lock-authority manifest on a repository-owned branch directly parented to current `main`, and keeps the generated commit bound to canonical `github-actions[bot]` provenance. The promotion PR itself is created by a separate repository-scoped GitHub App so GitHub treats its `pull_request` event as an external App event rather than a `GITHUB_TOKEN`-suppressed event; CI and CodeQL can therefore register normally on the exact promotion head.

The promotion-author App credential is available only to the default-branch `dependency-promotion-author` workflow, which runs from reviewed `workflow_run`/schedule wakes, checks that its trusted workflow SHA is still exact live `main` before any mutation, and mints an installation token requesting only `pull-requests: write`. Repository variables bind the expected App login and numeric bot id; missing, malformed, collapsed, or mismatched identity fails closed. Generated commits/refs and guarded merge continue to use the native repository token, while the App token is used only for PR creation. Major GitHub Actions updates remain manual. Dependabot native rebasing is enabled; governance never updates a Dependabot source branch itself.

Because `main` requires the dedicated `Trusted PR Gate`, dependency governance never publishes that authority itself. The default-branch Trusted PR Auto Gate must first publish an exact App-owned success from a genuine `schedule` run. Immediately before merge, the dependency controller fresh-rebinds the PR and then independently requires workflow id/path/name, `event=schedule`, `run_attempt=1`, exact current-main base, exact PR/base/head/prospective-merge parents and tree, repository identity, and the dedicated App status. Only then may it request the SHA-guarded merge. Owner-routine `workflow_run` gate evidence remains valid for its separate owner lane but is insufficient for dependency merge authority.

After any governed dependency merge, the controller re-reads the actual merge commit and requires exact ordered base/head parents, a merge tree identical to the validated dependency head, and the merge SHA as current `main`. It then requires a single canonical attempt-1 CI registration for that exact resulting main. If no automatic `push` CI has registered yet, the controller may dispatch the reviewed `ci.yml` from trusted `main` with exact `subject_sha`/`subject_ref=main` inputs and boundedly wait for that new `workflow_dispatch` registration. Wrong workflow identity, ambiguity, a terminal failed run, registration timeout, or main drift fails closed. For Python promotions, the workflow emits its `merged=true` handoff only after this post-merge continuity proof completes.

## Red-path recovery

Recovery has no merge or status authority. It may request at most one rerun (`maxRunAttempts == 2`) and only when all of these conditions are true:

- the PR first passes the same Dependabot identity, provenance, current-base, control-plane, and semantic-diff checks used by governance;
- the failed run is the reviewed CI workflow for the exact PR head;
- exactly one non-aggregate leaf job failed;
- exactly one step in that job failed and the step is in the code-owned infrastructure/upload allowlist;
- a timestamp-bounded slice of that failed step's logs contains an approved transient network/service signature;
- no deterministic dependency, policy, authentication/authorization, rate-limit, disk, or permission blocker appears in that same log slice.

Tests, deterministic evaluations, supply-chain assertions, security scans, browser assertions, CodeQL, and aggregate gates are never recovery targets. A second failed attempt stays red for manual investigation.

## Code scanning

`codeql.yml` runs Python CodeQL with `security-extended` queries on pull requests, `main`, a weekly schedule, and manual dispatch. External-fork pull requests do not receive write-capable code-scanning execution.
