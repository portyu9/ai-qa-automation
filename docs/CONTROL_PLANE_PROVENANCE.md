# Trusted Control-Plane Provenance

> [!IMPORTANT]
> **Control-plane provenance identifies the trusted controller/configuration subject used by a run. It does not prove test correctness, authorize mutation, or convert an unverified outcome into PASS.**

## Purpose

A target Git SHA identifies the system under test; it does not identify the controller that interpreted policy, exposed tools, loaded project Skills, or produced the report. The runtime therefore binds a separate, content-addressed trusted control-plane subject before model or target-tool execution.

The subject has two independent manifests:

1. **Project authority** under `control_root`: `CLAUDE.md`, explicit presence/absence of `.mcp.json`, and the complete `.claude` namespace. The five Skills requested by the Agent SDK and `.claude/settings.json` are required regular-file inputs.
2. **Controller package authority**: the complete live `ai_qa_automation` package source/resource namespace. `__pycache__` is excluded because generated bytecode caches are not configuration/source authority.

Each manifest persists canonical relative paths, file sizes, SHA-256 content hashes, directory namespace, explicit optional-path absence, total ingested bytes, and a manifest digest. Raw control-plane file contents are not copied into run state, reports, lineage, or attestations.

## Git is supporting metadata, not authority

When the project control root is a safely inspectable Git repository, provenance also records the exact commit SHA and whether the worktree was clean at the observation point. A Git SHA never substitutes for live-file capture: dirty or untracked `.claude` authority remains part of the manifest.

Startup uses a capture → Git observation → capture sandwich. Git metadata is attached only when both bounded filesystem captures identify the same content and the same ownership observation. This prevents a clean commit label from being attached to different live authority bytes.

In non-Git or installed-package contexts the Git fields can be absent. The two live content manifests remain the authority subject.

## Runtime binding and terminal truth

The initial subject is persisted in canonical `AgentRunState` before model execution and propagated into the final report, run lineage, and unsigned run attestation. It remains distinct from `target_git_sha`.

Immediately before every Agent SDK session attempt, including a bounded retry after a replay-safe startup failure, the runtime recaptures the trusted control-plane subject and requires exact content plus filesystem-observation equivalence with the run-start binding. A drifted subject refuses provider construction as `BLOCKED`; an unsafe or unavailable subject refuses provider construction as `INFRASTRUCTURE_FAILURE`. A later byte-for-byte restoration cannot erase that earlier pre-provider denial.

Terminal revalidation has explicit states:

| Status | Meaning |
|---|---|
| `NOT_CAPTURED` | No subject was established. |
| `BOUND` | A run-start subject was captured, but no terminal comparison was required/performed on this path. |
| `VERIFIED` | Terminal content and ownership observation matched the bound subject. |
| `DRIFTED` | Terminal content or authority ownership/metadata differed. |
| `UNAVAILABLE` | The terminal subject could not be observed safely and completely. |

Candidate `SUCCESS` is fail-closed: `DRIFTED` demotes it to `BLOCKED`; `UNAVAILABLE` demotes it to `INFRASTRUCTURE_FAILURE`. A pre-existing non-success outcome is preserved rather than overwritten merely because provenance later drifted or became unavailable. Provenance status still records that additional truth.

No provenance status itself is a validation PASS.

## Filesystem and resource authority

Capture is descriptor-relative and no-follow. Symlinks, special files, unreadable authority entries, incomplete scans, root replacement, namespace change during capture, and file identity/content change during a confined read fail closed.

Bounds apply to:

- directory-entry observations;
- each ingested regular file;
- aggregate project/controller file bytes;
- canonical UTF-8 path length;
- persisted manifest entry counts; and
- canonical manifest metadata serialization.

File ownership metadata intentionally detects same-byte authority rewrites/replacements. Directory observation binds ownership/mode without volatile timestamps so creation or churn inside excluded `__pycache__` directories does not create false control-plane drift.

## What the subject proves—and does not prove

The subject proves which filesystem source/configuration bytes and namespace were observed by the deterministic controller boundary at capture time, plus optional Git context. It does not cryptographically attest already-loaded Python code objects or in-memory interpreter bytecode. The controller-package manifest is therefore described as the live installed/source filesystem subject, not as a hash of process memory.

Transient changes entirely between discrete captures cannot be reconstructed after the fact; the runtime prevents terminal `SUCCESS` unless the terminal subject revalidates, but it does not claim continuous filesystem monitoring.

The run attestation remains unsigned integrity metadata. Including the control-plane subject in that attestation does not certify the controller, the target, or the QA outcome.

## Core separation

```text
trusted control-plane subject  !=  target repository subject
configuration identity         !=  validation PASS
integrity metadata              !=  correctness
Git commit context              !=  live authority manifest
```

The authority invariant remains: **missing, ambiguous, drifted, or unsafe control-plane provenance cannot manufacture verified success.**
